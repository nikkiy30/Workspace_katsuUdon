## 目的と価値の仮説

Chopは、食材を買う前に迷う人が、過去の廃棄記録と生活パターンを参考に購入・使い切りを判断するアプリ。READMEの説明を現在の目的の出発点とする。食品ロス削減、節約、助言への納得感は**利用者に確認すべき価値の仮説**であり、実装済み画面やハッカソン受賞だけでは効果を実証しない。

本人から「初回設定から記録までの使いやすさ」を優先する回答を受けた。[変更001](changes/001-startup-checks.md)で既存のHook・型検査問題を直し、[変更002](changes/002-onboarding-to-record.md)で保存失敗・再試行・完了案内を改善する。いずれも人間のレビュー前の初実装である。

## 変更を進める単位

1. `changes/`に「誰のどの困りごとか、変える振る舞い、受け入れ条件、含めない範囲、データ・画面・運用への影響」を短く記す。未確定の価値判断は早めに確認し、独立した調査・実装は続ける。
2. 選択肢と採用理由を記し、既存機能・ブランチを利用して小さく実装する。正常時だけでなく未設定、0件、失敗、取消、再読込、旧データの扱いを明記する。無関係な修正を混ぜない。
3. 下の品質区分ごとに結果を残す。「成功」「失敗」「未実施」「対象外」を区別する。必要な境界条件・障害を試す。実装と同じ処理を繰り返すだけのテストは増やさない。
4. AI出力を**人間がレビューできる初実装**として提出する。人間の判断・修正・再検証を同じ記録に追記する。目的や受け入れ条件が変われば設計・実装も見直す。
5. mainを直接変更・pushせず、専用ブランチへコミット・pushしてmain向けPRを作る。コミット→push→PR→マージ→デプロイ→公開後確認を別々に記録する。本人のレビュー前にマージやデプロイへ進めない。明示的な依頼や既存の権限範囲を確認し、公開・他者への送信を自動で行ったことにしない。

技術面の受け入れ条件が通っても、利用者が理解し、役立つと判断するまでは「利用者にとって完成」としない。AIの生成行数・コミット数を価値の代用にしない。

## 現在使えるローカル検証

前回の環境是正は`/workspace/cloud-security`に保持している。これはこのマシンの環境用資料であり、このGitリポジトリ単体には含まれない。別環境で同じ絶対パスがあるとは仮定しない。

```bash
# このクラウド環境では、各シェルで検証済みの分離ツールを有効にする
source /workspace/cloud-security/activate.sh
python3 /workspace/cloud-security/scripts/check-runtime.py
cd /workspace/Workspace_katsuUdon
./node_modules/.bin/tsc --noEmit
npm test
CI=1 EXPO_OFFLINE=1 npm run lint
CI=1 EXPO_OFFLINE=1 npx --no-install expo export \
  --platform android --output-dir dist/review-001 --max-workers 2
```

変更001では通常の型検査とAndroid exportが成功し、Lintは0エラー・34警告だった。`--allowImportingTsExtensions`による迂回は不要。002の最終差分でも同じ検査が成功し、追加したNode24の組み込みrunnerによる`npm test`で保存・読取の障害と境界の7テストが成功した。typecheck用npmコマンドとGitHub Actions設定は未追加。ネイティブUI試験・CI整備は[未解決項目](backlog.md)で追跡する。詳細は変更002の品質区分ごとの結果を参照する。

実機検証には配布・接続手段と端末が必要。開発サーバーやmanifestだけで初回設定の完了・データ保存を確認済みにしない。実データを試験用に消去しない。

環境安全性の根拠・保留操作・起動時／週次／緊急更新手順は`/workspace/cloud-security/REPORT.md`、`RUNBOOK.md`。元のOS・管理ランタイム・Git HTTPS等には提供側の残作業がある。分離版の起動時検査が失敗したら、該当する外部取得・圧縮入力処理を保留する。公開情報の取得には許可された宛先、既存CA・プロキシ、時間・サイズ制限、Brotli非展開または修正済み取得器を使う。
