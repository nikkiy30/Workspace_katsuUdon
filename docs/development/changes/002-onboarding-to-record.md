# 002：初回設定を確実に保存し、記録の入口へ進む

日付：2026-10-26（日本時間）。状態：人間レビュー前の初実装。変更001の上に積む別のレビュー単位。ブランチ公開以降の状態は開発の入口と実際のGit／PRで確認する。

## 目的・受け入れ条件

利用者は、初回設定に答えた後、保存できたか分からないまま先へ進んだり、自動遷移で案内を読み逃したりすると、記録を始めにくい。本人から「初回設定から記録までの使いやすさ」を優先する回答を受け、この改善を選んだ。方向性の選択は、実装の承認や価値の検証とは区別する。

今回変える振る舞い：保存成功の条件を明確にし、失敗時に回答を残して再試行できるようにする。起動時の読取失敗を新規利用と混同しない。完了案内を本人が読み終えるまで残し、ホームの既存「廃棄入力」へつなぐ。

受け入れ条件：

1. 未回答・空白だけの回答は保存しない。プロフィール保存失敗で完了フラグを書かず、フラグ保存の失敗も成功扱いしない。
2. Q3の保存失敗時は同じ画面・回答を保ち、再試行を案内する。保存中の同じボタンの連打では保存を開始し直さない。
3. 起動時の読取失敗・解釈できない旧フラグは不明として扱い、データを消さず再読込を案内する。既存のtrue/false/nullは意味を保つ。
4. 親子のProviderを1つにそろえる。非表示の起動画面が完了後の画面を横取りせず、保存中に離れた画面から後で勝手に完了へ移動しない。
5. 完了画面は3秒で自動移動せず、「ホームへ進む」で進む。記録する食材がない人にも開始を強制しない。ホームの「廃棄入力」へ進めるかは実機レビューする。
6. 境界・障害テスト、通常の型検査、Lint、Androidバンドル生成を実行する。技術チェックとUI・利用価値の結果を分ける。

対象外：廃棄記録フォーム自体の保存処理、AIコスト計算、AI障害、カレンダー保存、DB移行、途中回答の端末再起動をまたぐ永続化、認証、CI追加、リモート操作、公開。

影響：既存SQLiteスキーマ、profileの固定ID、AsyncStorageのキーとtrue/false値、ホームの導線は維持する。プロフィールは先に保存し、完了フラグを後に保存する。2ストアを原子的に更新できるようになったとは扱わない。変更001とは別にpackage.jsonへtestコマンドを追加するが、新依存やlockfile変更はない。

## 選択肢・設計判断

- 2ストアの統合／マイグレーションより、既存の保存形式を維持してエラー伝播を直す小さい差分を選んだ。フラグだけ失敗したときSQLiteのプロフィールは残る。再試行は既存UserDBの固定IDへの保存を使う。実DBでの再試行は実機で確認する。
- 永続化の契約を`services/onboardingPersistence.ts`へ分離し、保存先の障害を注入して試験する。正常な戻り値だけを並べたテストではなく、「片方だけ成功」「失敗後の再試行」「書込待ち」「旧データ不明」を確認する。
- 完了画面から廃棄入力を自動で開く案は採らない。廃棄した食材がない利用者もいるため、ホームへ進む選択を残す。
- 完了フラグ読取失敗をfalseへ変換する従来挙動をやめた。未知の文字列は自動修復・消去せず保留する。再試行で直らない旧形式は、担当がバックアップと移行方針を確認する必要がある。
- 新しいテスト依存は入れず、Node24の組み込みtest runner／TypeScript型除去を使う。MODULE_TYPELESS_PACKAGE_JSON警告は残るが、既存のCommonJS設定へ影響するpackage全体の`type: module`変更はしない。

## 実装の対応

| 条件 | 実装 |
|---|---|
| 保存の契約・未知フラグ | `services/onboardingPersistence.ts`、`hooks/useOnboarding.tsx`。両方の書込後だけ成功とする。回答値をログへ出す処理も削除 |
| 保存中・失敗・再試行 | `app/(onboarding)/question3.tsx`。refで同時開始を抑止し、busy/disabledと案内を表示。離脱後の遷移をフォーカスで抑止 |
| 状態の一貫性・読取不明 | `app/(onboarding)/_layout.tsx`の重複Providerを除去。`app/index.tsx`はフォーカス中だけ遷移し、読取失敗では再読込画面を出す |
| 自分で完了案内を読む | `app/(onboarding)/complete.tsx`。タイマーを除去し、記録の入口・0件時の案内を示す |
| 検証 | `tests/onboarding-persistence.test.mjs`と`npm test`。Node24で実行 |

## 状態の扱いと限界

| 状態 | 今回の扱い |
|---|---|
| 初回・未回答 | 未回答を保存せず、Q3から戻って回答確認できる。初回nullフラグは従来どおり未完了 |
| 保存中 | ボタン文言とbusy状態、選択・画面上の戻るボタンを無効化。直前の連打もrefで抑止 |
| SQLite失敗 | 完了フラグへ進まない。回答を残して再試行 |
| フラグだけ失敗 | 完了扱いにせず再試行。保存済みプロフィールは削除しない |
| 読取失敗 | 不明のまま再読込。0件や未設定と同一扱いにしない |
| 旧フラグtrue/false/null | 既存の意味を維持。未知の文字列は保留。自動消去・推測による変換なし |
| 取消・離脱 | 保存前は戻れる。OS操作等で保存中に離れても、完了後の自動遷移は抑止。開始済みのストレージ書込自体を取り消せるわけではない。実機で要確認 |
| 端末終了・再起動 | 完了フラグを読み直す。未保存の回答はメモリー上だけなので残らない。フラグtrue・profile欠落という既存不整合の検出は今回未対応 |
| 記録0件 | 廃棄がなくてもホームへ進める。実際の記録保存・ホーム集計・AI評価は今回の変更で検証したとはしない |

小さい画面でもQ3のエラー案内まで到達できるようScrollViewを追加し、ボタン・ラジオ選択・エラーのアクセシビリティ属性を付けた。完了説明の色と注記の文字サイズも調整した。ただし読上げ、文字拡大、スクロール、色・操作性の実機確認は未実施。

## 人間にレビューしてほしい点

1. 初回からQ3まで答え、保存後に案内を読む時間があり、ホームの「廃棄入力」を迷わず見つけられるか。

3. 廃棄がない人への案内が、不要な記録や罪悪感を促していないか。
4. 端末再起動、OSの戻る、文字拡大、読上げでも操作が成立するか。記録保存後のホーム表示は別途確認する。
