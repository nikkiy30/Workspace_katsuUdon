## 今回変えることと受け入れ条件

困る人は、SDK更新を取り込む開発責任者と、記録・カレンダー・AI画面を使う利用者。SDK更新後のLint増分を整理し、品質確認を通すためのコード案を提示する。

変える振る舞いは、画面表示のための重複状態を減らし、初期化と非同期完了・画面離脱の扱いを明確にすること。受け入れ条件は、ルールを無効化せずLintエラー0件、通常の型検査成功、Android/iOSバンドル生成成功、抽出した集計ロジックと旧SQLiteスキーマの試験が通ること。

含めない範囲：元PRへの直接push、mainへの変更、マージ、配布、APIキー構成の変更、DB形式や実利用者データの変更、全警告の修正、PR #3の統合、実機確認済みという宣言。

## 原因の分類

PR #2の固定baseでは`npm run lint`が1エラー・34警告、SDK57のheadでは27エラー・34警告になった。原因はeslint-config-expo更新でReact Hooksの検査が増えたこと。**26件の実行時バグをSDK更新が作ったという意味ではない。**

| ルール | 元PRのLint内の件数 | 意味と修正案 |
|---|---:|---|
| rules-of-hooks | 1（既存） | コンポーネント外でuseRouterを呼んでいた。start画面の中へ移す |
| immutability | 11 | Effect等から後方のconst関数を参照する構造を新しい解析が検出。呼ぶ関数を先に定義し、不要なEffectを除去する。通常のJS実行で毎回ReferenceErrorになるという意味ではない |
| set-state-in-effect | 6 | props・保存データから同期的に状態を複製して、追加描画や二重処理を生む構造。計算で出せる値は計算し、初期値はlazy initializer、外部処理の結果は非同期完了時に更新する |
| purity | 3 | クイック返信のDate.nowが検出された。呼出し元はonPressであり、描画時に実行されたとは確認していない。押下用処理をuseCallbackで明示し、再描画による参照の変化も整理すると検出が解消した |
| refs | 6 | Animated.ValueをuseRef(...).currentで描画中に取得する従来の書き方を検出。アニメーション値の参照をuseStateのlazy initializerで安定させ、起動・停止はEffectへ置く |

app/componentsに加えてhooksも直接検査すると、useOnboardingのimmutabilityがさらに1件見つかった。それも同じ原因として直した。修正途中で、先頭の宣言順エラーを直すと後続のset-state-in-effectが見える場合があったため、一回のLint結果だけで終了しなかった。

## 採った方法と代替案

新しいルールを一括でoff/warnへ落とす案は採らなかった。短期の段階移行として例外を使うなら、対象・理由・担当・期限を明記する別の判断が必要。この案ではコード側を整理した。`eslint.config.js`、依存バージョン、lockfile、database配下は未変更。

| 対象 | 修正 | 意図して変わる点・確認が必要な点 |
|---|---|---|
| カレンダー | markedDatesを食材・選択日・基準日から計算する純粋関数へ。食材読込はPromise完了時に反映し、日付はフォーカス時に更新 | 選択日のマークと使用日・期限の重なりを維持。描画中に時刻取得し直さない。開いたまま日をまたぐ表示は実機確認が必要 |
| 使用日モーダル | 開いている食材ごとに子コンポーネントを作り、期限の初期値を初期化時に決める | 取消で閉じて開き直したとき、未保存の選択日・数量は残さない。別の食材へ状態が流用されない |
| プロフィール | 編集画面の読込を初期値へ。フォーカス再読込の関数を先に定義 | 編集値がEffectの後着で上書きされる機会を減らす。同期DB読込の初回表示コストは実機で要確認 |
| 廃棄サマリー | 月カードと一覧を同じ読取スナップショットから計算。初期選択を今月にし、集計用Effectと重複状態を除去 | 初期の0件カード→集計後カードによるAI提案の重複起動を減らす。画面を開いている間の外部更新を自動購読する設計ではない |
| AIチャット | 初回リクエストと結果の状態更新を分離。画面を離れた後の結果反映を抑止。診断入力は画面セッション開始時に固定 | 同じ画面インスタンスへのsetParamsで別診断へ切替える機能は対象外。ネットワーク送信そのものの取消・完全な重複排除は実装していない |
| Home / Toast | route paramsから表示を導出し、終了時に消す。Animated値を一度作り、タイマーとアニメーションをcleanupで停止 | 以前の100ms後のパラメータ消去をやめ、Toast終了時に消す。再表示、離脱、duration変更は実機で確認する |
| 初回設定Hook | AsyncStorage読取をPromise完了時に反映し、unmount後の状態反映を抑止 | PR #3で扱う保存失敗の契約変更は持ち込まない。既存のエラー時falseという扱いもここでは維持 |

EffectからのsetStateを単にsetTimeoutで遅らせてLintを隠す変更はしていない。初期化・導出・外部処理の役割を分けた。既存コードの同期DBメソッドを使うため、初期描画中の読込量が増える画面がある。大きい記録件数での体感速度は未検証であり、必要なら非同期DB APIへ移す別変更を検討する。

## 検証

実行ツールはこの環境で検証済みのNode24.22.1等を使用した。新しいテスト依存は追加していない。`npm test`はNode24の組み込みrunnerを使い、既存のTypeScript6で実際のschema.tsを試験用に変換する。

| 確認 | 結果 |
|---|---|
| Lint | エラー0件・警告26件、終了コード0。ルール・警告を一括で無効化していない |
| 通常のtsc --noEmit | 成功、終了コード0 |
| Android/iOS Expo export | 両方成功、各終了コード0。ネイティブビルドと実機試験とは別 |
| npm test | 7成功、失敗・取消・skip各0 |
| 集計の境界 | 年越しの3か月、0件、各週境界、表示外月、不正日付、旧SQL形式、入力の非破壊性を確認 |
| カレンダー | 空データの選択日、使用日・期限の重なり、期限切れ色、保存データの非破壊性を確認 |
| 旧SQLiteスキーマ | 合成のDBファイルへ旧waste_recordsを作り、**実際のDatabaseSchema.createTables()**を呼び、cost追加前の記録・ID・日時、再初期化後の値、ファイルを閉じて開き直した後の保持を確認 |

SQLite試験の接続先はNodeのSQLiteであり、Expo57のネイティブブリッジではない。実利用者のDBを読んだり消したりしていない。削除するのは試験自身が作った一時ディレクトリだけ。これで「SDK更新後の実端末でもデータが失われない」とは証明しない。NodeのSQLite実験的API／module typeに関する警告も、アプリの実機結果と区別する。
